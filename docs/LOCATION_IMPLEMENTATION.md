## 1. Результаты анализа

### 1.1 Текущая модель "региона" — один плоский текстовый столбец

Во всём проекте локация машины/заявки/пользователя — это **один текстовый столбец `region`**,
без какой-либо иерархии регион → город → район. Значение на самом деле не "регион" (область), а
**название города**: единственный источник значений — жёстко зашитый список из 8 казахстанских
городов во фронтенде (см. 1.6). Ни таблиц, ни FK, ни справочников регионов/городов/районов в
проекте **нет** (проверено grep по `district`, `oblast`, `city_id`, `region_id` — ноль совпадений
во всём репозитории).

Таблицы, где присутствует `region`:

| Таблица | Столбец | Тип | NOT NULL | Где создан |
|---|---|---|---|---|
| `listings` | `region` | `text` | да | `backend/migrations/00002_create_listings.sql` |
| `buyer_requests` | `region` | `text` | да | `backend/migrations/00004_create_buyer_requests.sql` |
| `users` | `region` | `text` | **нет** (nullable) | `backend/migrations/00001_create_users.sql` |

`users.region` фактически никогда не записывается приложением: в
`backend/internal/repository/users.go` нет ни одного `INSERT INTO users`, где передавался бы
`region` — колонка есть в схеме, но недостижима из UI/API (форма регистрации её не запрашивает).
На странице профиля (`frontend/components/dashboard/ProfileContent.tsx:28`) значение только
**отображается** (`user.region ?? "не указано"`), формы редактирования нет.

### 1.2 Backend — структура

- Go 1.25, Gin, PostgreSQL 17, миграции — Goose (`backend/migrations/000NN_*.sql`, `-- +goose Up` /
  `-- +goose Down`), доступ к БД — `pgx/v5` (`pgxpool.Pool`).
- Слои: `internal/handlers` (HTTP) → `internal/repository` (SQL) → `internal/models` (структуры) →
  `internal/service` (бизнес-логика: Auto Exchange / daily tick / matching).
- `region` передаётся как обычная `string`/`*string` без валидации набора значений — ни `CHECK`,
  ни enum, ни FK. Валидируется только "не пусто" (`binding:"required"` / `min=1` на бэкенде,
  `z.string().min(1, "Выберите регион")` на фронтенде).

### 1.3 Frontend — структура

- Next.js 16 (App Router), React 19, react-hook-form + zod, Tailwind v4. Локация выбирается через
  обычный `<Select>` (`components/ui/Select.tsx`), опции — статический массив `regions` из
  `frontend/lib/mock/cars.ts:429-438`.

### 1.4 Таблицы/справочники регионов, городов, районов — **отсутствуют**

Ни в одной из 13 миграций (`00001`…`00013`) нет таблиц `regions`, `cities`, `districts` или
аналогичных. Нет seed-файла с географическими данными — `backend/cmd/seed` существует (сидинг
тестовых объявлений/пользователей для разработки), но городов/регионов не сидирует, а лишь
использует те же строковые значения из `regions`, что и фронтенд.

### 1.5 Как сохраняется регион автомобиля

`models.Listing.Region string` (`backend/internal/models/models.go`) → колонка `listings.region`
(`text`, `NOT NULL`). Записывается один раз при создании (`ListingsHandler.Create`,
`createListingRequest.Region string \`binding:"required"\``) и может быть изменён владельцем через
`PATCH /api/listings/:id` (`updateListingRequest.Region *string`) или администратором через
`PATCH /api/admin/listings/:id` — оба пути в итоге вызывают
`ListingRepository.UpdateListing(..., fields map[string]any, ...)`, где `region` — просто одна из
строковых колонок наравне с `make`/`color`/`description`. Особой логики (нормализация,
валидация по справочнику) нет.

Индекс: `idx_listings_make_model_region ON listings (make, model, region)` — составной, для
каталога/поиска.

### 1.6 Как регион используется в поиске и в Match

**Поиск/каталог** (`GET /api/cars`, `frontend/features/listings/filterCars.ts` ↔
`backend/internal/repository/listings.go: ListingFilters`): точное строковое сравнение —

```go
if f.Region != "" {
    add("region = $%d", f.Region)   // listings.go:78-79
}
```

Регион в фильтре не является диапазоном/иерархией — просто `region = 'Алматы'`.

**Auto Exchange Match** (`backend/internal/service/exchange.go:createMatches`, ~L213-230) — регион
входит в критерии подбора пары listing↔buyer_request **как точное строковое равенство**:

```sql
JOIN buyer_requests br ON
    br.status = 'active' AND
    l.status = 'active' AND
    l.is_exchange = true AND
    l.user_id <> br.user_id AND
    l.region = br.region AND      -- <-- точное совпадение региона
    l.make = br.make AND
    l.model = br.model AND
    l.year BETWEEN br.year_from AND br.year_to
WHERE l.price > 0
  AND abs(l.price - br.current_offer)::numeric / l.price * 100 <= $1::float8
```

Это часть основного алгоритма Match (регион, марка, модель, год, цена — как описано в
skill `auto-exchange-match`). **Любое изменение источника значения `region` в этом запросе — это
изменение алгоритма Match**, что прямо запрещено правилом №3 задания. Переход с текстового
сравнения на сравнение по `city_id` возможен только как **эквивалентная замена представления
данных** (то же самое "то же место"), и по правилам задания требует отдельного явного
подтверждения пользователя перед тем, как трогать `exchange.go` (см. план миграции, этап 8).

## 2. Обнаруженные таблицы и API — сводка

**Таблицы:** только `listings.region text`, `buyer_requests.region text`, `users.region text
NULL`. Справочных таблиц регионов/городов/районов нет.

**API:**
- `GET /api/cars?region=...` — фильтр каталога, точное совпадение строки.
- `POST /api/listings`, `PATCH /api/listings/:id`, `PATCH /api/admin/listings/:id` — `region` как
  свободная строка в теле запроса, без сверки со справочником.
- `POST /api/requests` (buyer request) — аналогично.
- Эндпоинтов для получения списка регионов/городов/районов **не существует** — фронтенд использует
  захардкоженный локальный массив, backend вообще не отдаёт список локаций.

**Несогласованность, обнаруженная в ходе анализа (не относится к текущей задаче напрямую, но
важно для плана):** список из 8 городов существует в **двух местах** — `frontend/lib/mock/cars.ts`
и отдельно в Go-сидере (`backend/cmd/seed`) — без единого источника истины. Новая схема
регион/город/район должна стать единственным источником истины для обоих.

## 3. Необходимые изменения (высокий уровень)

1. **Новые справочные таблицы** (аддитивно, не трогая существующие): `regions` (области +
   Астана/Алматы/Шымкент как отдельные единицы республиканского значения), `cities` (привязаны к
   `region_id`), `districts` (привязаны к `city_id`, актуально в основном для Алматы/Астаны/
   Шымкента — большинство городов без районного деления).
2. **Новые nullable FK-колонки** на `listings`, `buyer_requests`, `users`:
   `region_id`, `city_id`, `district_id` — добавляются рядом с существующим `region text`, не
   заменяя и не удаляя его на первом этапе.
3. **Новый read-only API** `GET /api/locations/regions`, `GET /api/locations/cities?regionId=`,
   `GET /api/locations/districts?cityId=` — отдаёт справочник для каскадного `<Select>`.
4. **Новый фронтенд-компонент** (каскадный выбор регион → город → район), визуально идентичный
   существующему `<Select>` (тот же `components/ui/Select.tsx`, те же классы/отступы/шрифты —
   правило №1 запрещает менять дизайн), подключаемый в 5 существующих точках использования
   (раздел 1.9) без изменения остального вида форм.
5. **Backfill существующих данных**: 8 текущих значений `region` — это на самом деле города,
   их нужно сопоставить с новыми `city_id` (и производным `region_id`) без потери и без угадывания
   несопоставимых значений.
6. **Отложенное изменение** (требует отдельного подтверждения пользователя, т.к. затрагивает
   Match): переключение `l.region = br.region` в `exchange.go` и фильтра каталога на сравнение по
   `city_id`. Сам алгоритм Match (набор критериев: регион, марка, модель, год, цена ±допуск) не
   меняется — меняется только то, **как** сравнивается "то же место" (строка → id).

## 4. План безопасной миграции данных

Все шаги — **аддитивные и обратимые** (`CREATE TABLE`, `ADD COLUMN ... NULL`), ни один не удаляет
и не переименовывает существующие столбцы на первом проходе.

1. **Миграция N: справочники.** `CREATE TABLE regions (...)`, `CREATE TABLE cities (...)`,
   `CREATE TABLE districts (...)` + сидирование данных (административное деление Казахстана: 17
   регионов, включая 3 города республиканского значения — Астана, Алматы, Шымкент; города/районы).
   Существующие таблицы не трогаются. `-- +goose Down` — `DROP TABLE` в обратном порядке.
2. **Миграция N+1: nullable FK-колонки.** `ALTER TABLE listings ADD COLUMN region_id uuid
   REFERENCES regions(id), ADD COLUMN city_id uuid REFERENCES cities(id), ADD COLUMN district_id
   uuid REFERENCES districts(id)` — аналогично для `buyer_requests`, `users`. Все `NULL`-able,
   без `NOT NULL` и без изменения существующего `region text`. Полностью обратимо (`DROP COLUMN`).
3. **Backfill (не в самой миграции, отдельный контролируемый шаг)** — одноразовый скрипт/
   `cmd/backfill-locations`, а не слепой `UPDATE` внутри goose-миграции: сопоставляет 8 известных
   строк (`Алматы`, `Астана`, `Шымкент`, `Караганда`, `Актобе`, `Павлодар`, `Атырау`,
   `Усть-Каменогорск`) с `city_id`/`region_id` по точному совпадению названия. Каждая строка,
   которая **не** нашла однозначного соответствия, логируется и оставляется как есть (`city_id =
   NULL`) — никаких угадываний/fuzzy-матчинга без ручной проверки. Прогон — вручную, с выводом
   отчёта "сколько строк сопоставлено / сколько нет", перед этим — snapshot/бэкап таблиц.
4. **Двойная запись (dual-write).** Backend при создании/редактировании объявления, заявки,
   профиля начинает писать **и** старое `region text`, **и** новые `region_id/city_id/district_id`
   одновременно. Все существующие чтения (каталог, Match, профиль) по-прежнему используют
   `region text` — поведение не меняется, риска регресса нет.
5. **Верификация.** Период стабилизации: сверка `region text` vs `city_id` на новых записях,
   мониторинг ошибок, ручная проверка расхождений.
6. **Отдельный, явно согласуемый этап:** переключение мест чтения (`ListingFilters.Region`,
   `exchange.go`'s `l.region = br.region`) на `city_id`. Выполняется **только после отдельного
   подтверждения пользователя**, т.к. правило №3 требует не менять алгоритм Match без явного
   разрешения — даже если по сути меняется только представление значения, а не сами критерии
   подбора.
7. **Деприкация `region text`** (удаление столбца) — не планируется в рамках этой задачи вообще;
   отдельное будущее решение после полной стабилизации, не раньше отдельного запроса
   пользователя.

## 5. План реализации по этапам

Каждый этап — небольшой, самодостаточный, **без автоперехода к следующему** (правило №5).
Ничего из этого не выполняется без отдельного запуска пользователем.

- **Этап 1 — Анализ.** Этот документ. Код не менялся, миграции не запускались. ✅ **завершён**.
- **Этап 2 — Справочные таблицы.** Миграция `regions`/`cities`/`districts` + сидирование данных
  административного деления Казахстана. Существующие таблицы/код не трогаются.
- **Этап 3 — Nullable FK-колонки.** Миграция, добавляющая `region_id/city_id/district_id` в
  `listings`, `buyer_requests`, `users`. Существующий `region text` не трогается.
- **Этап 4 — Read-only API справочника.** `GET /api/locations/regions|cities|districts` — новый
  handler/repository, никаких изменений в существующих эндпоинтах.
- **Этап 5 — Dual-write в backend.** `Create`/`Update` для объявлений, заявок и (опционально)
  профиля начинают заполнять новые FK-колонки наряду со старым `region text`. Чтение/поиск/Match
  не меняются.
- **Этап 6 — Backfill существующих данных.** Контролируемый скрипт с отчётом, снапшотом и ручной
  проверкой несопоставленных значений (см. раздел 4, шаг 3).
- **Этап 7 — Фронтенд: каскадный выбор региона.** Новый компонент (регион → город → район) на
  основе существующего `components/ui/Select.tsx`, без изменения дизайна/цветов/отступов.
  Подключение в 5 существующих точках (раздел 1.9), форма продолжает отправлять `region` (строка,
  для обратной совместимости) плюс новые ID.
- **Этап 8 — Переключение чтения (каталог + Match) на `city_id`.** Выполняется только по
  отдельному явному запросу пользователя — из-за правила №3 (не менять алгоритм Match без
  разрешения). Реализация: замена источника сравнения в `ListingFilters`/`exchange.go` при
  сохранении тех же критериев подбора.
- **Этап 9 (не запланирован, будущее решение)** — деприкация старого `region text`.

## 6. Этап 2 — подготовка схемы PostgreSQL (реализовано)

### 6.1 Миграция

номер после `00013`):

**`backend/migrations/00014_location_reference_tables.sql`**

### 6.2 Новые таблицы и связи

```
regions (id, name_ru, name_kz, slug UNIQUE, kind CHECK IN ('oblast','republican_city'), created_at)
   ↑ region_id (RESTRICT)
cities (id, region_id NOT NULL FK→regions, name_ru, name_kz, slug UNIQUE, created_at)
   ↑ city_id (RESTRICT)
districts (id, kind CHECK IN ('administrative','urban'),
           region_id FK→regions NULL, city_id FK→cities NULL,
           name_ru, name_kz, slug UNIQUE, created_at,
           CHECK: kind='administrative' ⇒ region_id set, city_id NULL
                  kind='urban'          ⇒ city_id set, region_id NULL)
```

- **Города республиканского значения (Алматы/Астана/Шымкент, требование №3):** моделируются как
  `regions.kind = 'republican_city'` — сам регион ЕСТЬ город. При импорте данных (этап 3) для
  каждого такого региона создаётся ровно одна дочерняя строка в `cities`, представляющая сам город
  — благодаря этому `listings.city_id`/`buyer_requests.city_id`/`users.city_id` всегда указывают на
  город независимо от того, находится ли он в обычной области или является городом
  республиканского значения. Дублирующего флага на `cities` не заводили — принадлежность к
  республиканскому городу определяется join'ом на `regions.kind`.
- **Различение районов (требование №4):** одна таблица `districts` с `kind` +
  `CHECK`-ограничением, которое требует ровно один заполненный родитель, соответствующий `kind`
  (`administrative` → `region_id`, `urban` → `city_id`). Проверено вставкой некорректной строки
  (`urban` с `region_id`) — отклонена `districts_check` (см. 6.4).
- **Новые nullable-колонки** на `listings`, `buyer_requests`, `users`: `region_id`, `city_id`,
  `district_id`, все `REFERENCES ... ON DELETE SET NULL` — удаление строки-справочника не удаляет
  и не блокирует реальные записи пользователей/объявлений/заявок. Существующий `region text`
  (включая `NOT NULL` на `listings`/`buyer_requests` и nullable на `users`) не тронут.
- Справочные таблицы между собой — `ON DELETE RESTRICT` (нельзя удалить регион/город, пока на него
  ссылается город/район) — защита от случайного разрыва иерархии при заполнении данных на этапе 3.

### 6.3 Индексы и ограничения целостности

- `UNIQUE(slug)` на `regions`, `cities`, `districts` — стабильный бизнес-ключ для будущего маппинга
  (см. 6.5), без коллизий из-за `NULL` (в отличие от составных UNIQUE с nullable-колонками).
- `idx_cities_region_id`, `idx_districts_region_id`, `idx_districts_city_id` — на справочных
  таблицах.
- `idx_listings_city_id`, `idx_buyer_requests_city_id`, `idx_users_city_id` — на существующих
  таблицах, т.к. `city_id` станет основным уровнем фильтрации (сегодняшний `region` фактически уже
  хранит название города, см. этап 1, раздел 1.1).
- `CHECK` на `regions.kind`, `districts.kind` и `districts` (XOR родителя) — валидированы вручную
  (раздел 6.4).

### 6.4 Стратегия безопасного маппинга текст → идентификатор (требование №5)

Импорт данных — Этап 3, поэтому справочники сейчас пусты. Стратегия для будущего backfill-скрипта
(Этап 6 общего плана, раздел 5):

1. При заполнении справочника на Этапе 3 каждому городу присваивается `slug` — нормализованный
   латинский идентификатор (например, `almaty`, `astana`, `ust-kamenogorsk`), однозначно
   соответствующий одному из 8 текущих значений `region` (`Алматы`, `Астана`, `Шымкент`, `Караганда`,
   `Актобе`, `Павлодар`, `Атырау`, `Усть-Каменогорск` — см. этап 1, раздел 1.1/1.6).
2. Backfill выполняется отдельным контролируемым скриптом (НЕ слепым `UPDATE` внутри goose-миграции):
   `UPDATE listings SET city_id = c.id, region_id = c.region_id FROM cities c WHERE listings.city_id
   IS NULL AND normalize(listings.region) = c.slug` (аналогично для `buyer_requests`, `users`).
3. Строки, для которых точного соответствия `slug` не нашлось, оставляют `city_id/region_id = NULL`
   и попадают в отчёт для ручной проверки — угадывание (fuzzy-match) исключено.
4. `region text` при этом не изменяется и не удаляется ни на одном шаге.

Это осталось на уровне задокументированной стратегии — по ограничению задания геоданные и, как
следствие, реальные строки для сопоставления не создавались на этапе 2.

### 7.5 Backfill текстовых `region` → `region_id`/`city_id`

Правила (см. `report()` в `cmd/import-locations/main.go`):
- Обновляются только строки, где `city_id IS NULL` — уже сопоставленные или сопоставленные вручную
  строки повторный запуск не трогает (идемпотентно).
- Сравнение **только точное**, без учёта регистра/пробелов (`lower(trim(region)) =
  lower(trim(city.name_ru))`) — никаких `ILIKE '%...%'`/частичных совпадений.
- Столбец `region` нигде не изменяется (в `UPDATE` не входит в `SET`).
- Совпадений без однозначного соответствия — оставлены `NULL`, без произвольного региона по
  умолчанию.
- Учёт написания на казахском не потребовался: единственный источник текста `region` сегодня — тот
  же фиксированный `<select>` с 8 русскими названиями (этап 1, раздел 1.1), свободного ввода нет,
  так что вариантов написания в реальных данных не существует; сопоставление тем не менее сделано
  регистро/пробело-независимым на будущее.

  выбран (`<select value={value.cityId ?? ""}>`) — отдельного шага «восстановления» не требуется.
  Реверс-lookup города→региона не нужен и не реализован: вызывающая сторона обязана передать
  оба id при контролируемом восстановлении (естественно для формы редактирования, которая читает
  оба поля из сохранённого объявления).
- **Защита от устаревших запросов** — каждый уровень кэшируется `react-query` по ключу с id
  родителя; при быстрой смене региона предыдущий («устаревший») запрос данных для старого
  `regionId` попадает в кэш под своим прежним ключом и никогда не рендерится, т.к. компонент
  всегда читает `useQuery` для ТЕКУЩЕГО `value.regionId`/`value.cityId`. Проверено отдельным
  тестом с управляемым (не сразу резолвящимся) промисом — раздел 10.4.
- **Алматы/Астана/Шымкент (`kind = republican_city`)** — `isSpecial` из ответа `/api/regions`
  определяет: город подбирается автоматически (единственная запись из
  `/api/regions/:id/cities`) через `useEffect`, интерактивный `<Select>` для города не
  рендерится — только статическая строка `Город: {название}`; сразу показывается выбор района.

### 10.4 Тесты (`LocationSelector.test.tsx`, 8/8 пройдено)

| Тест | Что проверяет |

### 11.2 Зависимый выбор и деривация текстового `region`

`LocationSelector` отдаёt только UUID (`regionId`/`cityId`/`districtId`). Легаси-поле `region`
(text) — то, что читает Match и хранится в БД для обратной совместимости — вычисляется в
`ListingForm` в `handleLocationChange`: название выбранного города, если он есть, иначе название
региона (тот же принцип, что уже описан в этапе 1: `region` исторически хранит самое конкретное
доступное имя места). Источник имён — тот же react-query кеш (`["locations","regions"]`,
`["locations","cities", regionId]`), что использует сам `LocationSelector` — повторного похода в
сеть не требуется.

- Смена региона → `cityId`/`districtId` сбрасываются (логика уже в `LocationSelector`, этап 5А).
- Смена города → `districtId` сбрасывается.
- Алматы/Астана/Шымкент (`kind=republican_city`) → `cityId` определяется автоматически,
  интерактивный выбор города не показывается (проверено на уровне `LocationSelector` в этапе 5А и
  сквозным тестом здесь — раздел 11.5).
- Район остаётся необязательным на всех уровнях — ни frontend, ни backend его не требуют.
- Город тоже необязателен: выбора одного региона достаточно для валидной отправки формы — как и
  раньше было достаточно выбрать место из плоского списка.

### 11.3 Backend

Существующий контракт `POST /api/listings` **расширен минимально** — новый DTO → Handler →
Repository → PostgreSQL, старый путь не переписан:

- `backend/internal/handlers/listings.go` — `createListingRequest` получил три новых optional поля:
  `regionId`/`cityId`/`districtId` (`binding:"omitempty,uuid"` — валидация формата UUID без новой
  библиотеки, штатный тег `go-playground/validator`, уже используется gin). Новый приватный метод
  `(*ListingsHandler) validLocation(...)`: если `regionId` задан — регион должен существовать; если
  `cityId` задан — `regionId` обязателен и город должен принадлежать именно этому региону; если
  `districtId` задан — `cityId` обязателен и район должен принадлежать именно этому городу. Любая
  нестыковка → `400 VALIDATION_ERROR`. Ничего не обязательно, если поле не прислано (полная
  обратная совместимость — старый клиент, не знающий об этих полях, получает точно то же
  поведение, что и раньше).
- `ListingsHandler` теперь принимает `*repository.LocationRepository` вторым параметром
  (`NewListingsHandler(listings, locations)`) — обновлены все 3 места создания (`cmd/api/main.go`,

- `backend/internal/repository/locations.go` — 2 новых read-метода: `CityRegionID` (город → его
  region_id) и `DistrictCityID` (район → его city_id, `false` для административных районов без
  city_id) — используются только для этой проверки принадлежности.
- `backend/internal/repository/listings.go` — `Create` теперь пишет `region_id, city_id,

## 12. Этап 5В — `LocationSelector` в редактировании объявлений (реализовано)

### 12.1 Где подключено

редактирования (введённый на этапе 5Б как временное ограничение) удалён полностью; `regions` из

и `components/admin/AdminEditListingContent.tsx` (админ) уже просто передают `listing` целиком,
новых полей от них не потребовалось.

### 12.2 Восстановление сохранённых UUID

`defaultValues` (ветка `isEdit`) теперь включает `regionId: listing.car.regionId ?? null`,
`cityId: listing.car.cityId ?? null`, `districtId: listing.car.districtId ?? null` — те же самые
поля, что и в create-режиме, просто с начальным значением из объявления вместо `null`. Дальше
работает уже реализованный на этапе 5А механизм `LocationSelector`: как только соответствующие
списки регионов/городов/районов догружаются, нужный `<option>` уже выбран — никакого отдельного
кода «восстановления» не потребовалось (компонент из 5А не менялся).

`GET`-ответы объявлений (`/api/dashboard/listings`, `/api/cars/:id`, `/api/admin/listings`,
избранное) теперь отдают `regionId`/`cityId`/`districtId` (`omitempty`) — этого не было после
этапа 5Б (тогда значения только писались, не читались); добавлено `backend/internal/handlers/
car_response.go` (3 поля) и `backend/internal/repository/listings.go`/`favorites.go`
(`listingColumns`/`favoriteListingColumns` + `scanListing`).

### 12.3 Старые объявления (только текстовый `region`)

`needsLegacyMatch = isEdit && !listing.car.regionId && !!listing.car.region` — если `regionId` не
сохранён, а текст `region` есть, запускается `resolveLegacyRegionText` (новая функция в
`frontend/lib/api/locations.ts`, не новый компонент): точное совпадение сначала среди названий
городов (все 20 регионов опрашиваются через уже существующий `listCitiesByRegion` — легаси-текст
исторически всегда был названием города, этап 1), затем — если совпадений среди городов нет —
среди названий регионов. 0 или 2+ совпадений → `null`, выбор остаётся за пользователем; **никакого
частичного/подстрочного совпадения** (проверено тестом: подстрока «Кокшет» от «Кокшетау» не
матчится). Результат применяется в `ListingForm` через `useEffect` **только в состоянии формы**
(`setValue`, `shouldValidate`) — ничего не пишется в PostgreSQL при простом открытии страницы;
запись происходит только через обычный сабмит формы (тот же путь, что и для любого другого поля).
Если пользователь успел сам что-то выбрать до того, как матчинг разрешился (`watch("regionId")`
уже не пусто) — авто-подстановка не применяется, руками введённое не перезаписывается.

### 12.4 Go API — обновление объявления

`PATCH /api/listings/:id` (владелец) и `PATCH /api/admin/listings/:id` (админ) — общий
`updateListingRequest` и `buildListingFieldUpdate` (существовали с более раннего этапа
редактирования, не с 5Б/5В) расширены тремя optional-полями `regionId`/`cityId`/`districtId`
(`binding:"omitempty,uuid"`), той же формы, что у `createListingRequest`.

- `validLocation` (была методом `*ListingsHandler`, теперь **свободная функция**, чтобы её
  использовали и владелец, и админ без дублирования) — регион существует; город принадлежит
  региону; район принадлежит городу — идентична проверке из этапа 5Б, переиспользована как есть.
- **Сброс при смене родителя реализован в `buildListingFieldUpdate`:** если `regionId` присутствует
  в запросе, `city_id`/`district_id` **всегда** записываются вместе с ним — `city_id = *CityID`,
  если он прислан, иначе `NULL`; то же для `district_id`. Поскольку `LocationSelector` на фронтенде
  уже обнуляет `cityId`/`districtId` при смене региона (и `districtId` при смене города, этап 5А) —
  единственный PATCH-запрос всегда несёт уже согласованное текущее состояние, и старый
  город/район не может «зависнуть» в объявлении.
- `AdminListingsHandler` получил третью зависимость `*repository.LocationRepository` (конструктор
  `NewAdminListingsHandler(listings, users, locations)`, main.go и `admin_test.go` обновлены).
- Новых миграций не потребовалось — все нужные колонки существуют с этапа 2.
- Права редактирования (`loadOwnedListing` — 403 для чужого объявления, admin-only middleware для
  админ-маршрута) **не менялись** — новая location-логика работает поверх той же проверки владения.

### 12.5 Согласованность текстового `region`

`backend/internal/repository/locations.go`: 2 новых read-метода, `RegionName`/`CityName`
(название по id). Новая свободная функция `resolveLocationText(ctx, locations, regionID, cityID)`
в `listings.go`: если `regionID` присутствует — берёт `CityName`, если есть `cityID`, иначе
`RegionName`, и **этим значением перезаписывается `req.Region`** ещё до вызова
`buildListingFieldUpdate`/создания объявления — то, что прислал клиент в поле `region`, в этом
случае полностью игнорируется. Если `regionID` не прислан — используется прежнее поведение
(текст клиента как есть, легаси-путь без изменений). Применено и к `Create` (этап 5Б get это
минимальное общее исправление, раздел 12 — раз правило одинаково для создания и редактирования,
хранить его только в одном из двух путей было бы несогласованно), и к обоим `Update`
(владелец + админ). Алгоритм Match и правила подбора покупатель/продавец не менялись — они по
прежнему просто читают `listings.region`, ничего не знают о UUID.

### 12.6 Что сохраняется в PostgreSQL

### 14.2 Восстановление сохранённых UUID

**`GET`-цепочка была неполной** — репозиторий уже сканировал `region_id`/`city_id`/`district_id`
(этап 6А, `buyerRequestColumns`/`scanBuyerRequest`), но JSON-ответ (`buyerRequestResponse`) их не

`regionId`/`cityId`/`districtId`; для легаси-заявки без `regionId` — результат `resolveLegacyRegionText`,
как только он придёт. Это не «эффект + setState», а чистое вычисление при каждом рендере — новых
данных в PostgreSQL при открытии формы не пишется, `PATCH` не отправляется, пока пользователь сам
не нажмёт «Сохранить».

листинги). Правило то же: точное совпадение сначала по городам, потом по регионам; 0 или 2+
совпадений → пользователь выбирает сам; ничего не пишется в БД до явного сабмита.

### 14.4 Go API — обновление заявки

`PATCH /api/requests/:id` (`backend/internal/handlers/requests.go`, `updateRequestRequest`)
расширен `regionId`/`cityId`/`districtId` (`binding:"omitempty,uuid"`), тем же способом, что и

- Проверка принадлежности — переиспользована **та же** свободная функция `validLocation` (уже

`parseCarFilters`). Домашняя `QuickSearch.tsx` (тоже строит `?region=...` на `/cars`, но не
относится к самому каталогу) — **не тронута**, что и подтверждает раздел 15.4 (старые ссылки с
текстовым `region` продолжают работать без переделки источника).

### 15.2 Go API поиска

`GET /api/cars` получил три новых optional query-параметра: `regionId`, `cityId`, `districtId`
(UUID). Новый `optionalUUIDQuery` (`validation.go`, рядом с `requireUUIDParam`) валидирует формат
до похода в БД — некорректный UUID → `400 VALIDATION_ERROR`, никогда `500`. Принадлежность города
региону/района городу проверяется **той же** свободной функцией `validLocation`, что уже
использовалась для объявлений и заявок (этапы 5Б/5В/6А/6Б) — без дублирования. `CarsHandler`
получил `*repository.LocationRepository` третьим полем (`NewCarsHandler(listings, locations)`,
main.go обновлён).

### 15.3 Логика фильтрации (приоритет, задокументирован в коде)

`ListingRepository.List` (doc-комментарий в коде даёт точное правило) — применяется **не более
одного** уровня местоположения, от наиболее конкретного:

1. **`districtId`**, если передан: `district_id = $1` — точное совпадение, без легаси-фолбэка
   (у старых объявлений вообще никогда не было информации о районе).
2. Иначе **`cityId`**: `city_id = $1` — тоже строго точное совпадение, **без** обращения к
   текстовому `region` (правило №2 задания: не включать объявления, для которых город не
   определён достоверно — то есть без `city_id`).
3. Иначе **`regionId`**: `region_id = $1 OR (region_id IS NULL AND region IN (SELECT name_ru FROM
   cities WHERE region_id = $1))` — единственное исключение, явно требуемое заданием (правило №1):
   объявление без `region_id`, но с точным текстовым совпадением на название ОДНОГО ИЗ городов
   этого региона (не подстрока — `IN`, точное сравнение), тоже считается принадлежащим региону.
4. Иначе, если `regionId` вообще не передан, а текстовый `region` есть: `region = $1` — байт в
   байт прежнее поведение, никаких изменений в этой ветке.

**Правило приоритета (задание требовало задокументировать):** если одновременно переданы
`region` (текст) и `regionId`, **`regionId` побеждает безоговорочно** — текст в этом случае вообще
не участвует в фильтрации. Не `OR` (могло бы неожиданно расширить выдачу за счёт несовпадающего
текста) и не `AND` (могло бы наоборот исключить корректные строки из-за случайно устаревшего
текста) — простое «текст полностью игнорируется, когда есть UUID» exclude обе проблемы разом.

Остальные фильтры (марка, модель, года, цена, тип кузова, коробка, привод, топливо), сортировка и
пагинация — тот же код `add()`-билдера `WHERE`, ни одна из существующих веток не переписывалась,
только добавлена одна новая перед ними.

### 15.4 Совместимость со старыми ссылками

`?region=Алматы` (без `regionId`) продолжает работать **без единого изменения кода** — эта ветка
условия (`case f.Region != "": add("region = $%d", f.Region)`) идентична дореформенной. Если
одновременно в URL оказались `region` и `regionId` (например, старая ссылка, к которой вручную

существующих URL не производится; фронтенд лишь ДОБАВЛЯЕТ `regionId`/`cityId`/`districtId` в URL
при НОВОМ выборе пользователя (см. 15.5) — старые закладки/ссылки, которые никто не трогал,
остаются буквально такими же, как были.

### 16.3 Как QuickSearch передаёт местоположение в каталог

По нажатию «Найти» (`handleSubmit`, единственная точка формирования URL) в `URLSearchParams`
добавляются `regionId`/`cityId`/`districtId` из `location` (только непустые — не добавляются
пустые значения) плюс легаси-текст `region`, выведенный **тем же способом**, что в `FilterForm`
этапа 7А: название выбранного города, если есть, иначе название региона — через два `useQuery`
(`listRegions`, `listCitiesByRegion`), результат которых на момент клика по кнопке уже почти
наверняка загружен (запрашиваются сразу при монтировании `QuickSearch`/при выборе региона).
Используется ровно тот же контракт параметров, что каталог уже принимает с этапа 7А — никаких
новых имён параметров, никакого нового backend-эндпоинта. Если регион не выбран — географические
параметры в URL не попадают вовсе (пустой `location` → `if (location.regionId) ...` не
срабатывает). Если выбран только регион — уходит `regionId` (+`region`), без `cityId`. Если выбран
город — `regionId`+`cityId`(+`region` с именем города). Если выбран район — все три (`regionId`,
`cityId`, `districtId`), так как `LocationSelector` физически не позволяет выбрать `districtId`
без уже выбранных `regionId`/`cityId` (район недоступен, пока не выбран город). Для Алматы/
Астаны/Шымкента (`kind = republican_city`) единственный город определяется и подставляется
автоматически самим `LocationSelector` (без изменений в этом этапе) — пользователь не выбирает
город повторно, но `cityId` всё равно попадает в URL. Остальные параметры (`make`, `model`,
`yearFrom`, `priceFrom`/`priceTo`) собираются той же логикой, что и раньше, без изменений.
