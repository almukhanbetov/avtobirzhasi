- `GET /api/regions/:id/cities` — для **Алматы, Астаны, Шымкента**: `kind=republican_city`,
  `isSpecial=true`, **ровно 1** город; районы этого города — Алматы 8, Астана 5, Шымкент 5

- Некорректный UUID (`/regions/not-a-uuid/cities`, `/cities/not-a-uuid/districts`) → **400
  VALIDATION_ERROR**, не 500.
- Синтаксически корректный, но несуществующий UUID (`00000000-...`) → **404 NOT_FOUND** с чистым
  сообщением («Регион не найден» / «Город не найден»), без утечки текста ошибки PostgreSQL.
- Payload, похожий на SQL-инъекцию (`1' OR '1'='1`), для path-параметра → **400 VALIDATION_ERROR**
  (отклонён на этапе валидации формата UUID, до похода в БД — не выполняется как SQL).

### 17.2 Воспроизведение и подтверждённая причина

разрешение промиса и коммит рендера.

**Классификация по разделу 2 задания: В — тестовая среда/таймаут**, не Б (тест не устарел — его
ожидания корректны и соответствуют действующему контракту), не А/Г (в реальном коде

## 19. Этап 8Б-3 — Исправление загрузки регионов в Next.js (реализовано)

### 19.1 Точная причина (установлена по фактическим данным, не предположена)

Заявленный симптом (QuickSearch на `http://localhost:3001` показывает «Не удалось загрузить
список, попробуйте позже», хотя `curl http://localhost:8081/api/regions` в браузере/терминале
работает) проверен пошагово:

1. **API_BASE_URL во фронтенде** — прочитан фактически скомпилированный клиентский чанк
   (`.next/dev/static/chunks/_0-6qmxe._.js`) уже запущенного dev-сервера: строка
   `const API_BASE_URL = ("TURBOPACK compile-time value", "http://localhost:8081/api") ??
   "http://localhost:8080/api";` — Turbopack инлайнит `process.env.NEXT_PUBLIC_API_URL` как
   `"http://localhost:8081/api"` (запятая — comma-expression, результат — второй операнд), значение
   однозначно `":8081"`. **Фронтенд обращается к правильному адресу** — это не причина.
2. **Сам API** — `curl http://localhost:8081/api/regions` без заголовка `Origin` → `200`, валидный
   JSON, 20 регионов. Подтверждает: сервер и данные в порядке.
3. **Тот же запрос с заголовком `Origin: http://localhost:3001`** (именно так его посылает
   браузер, но не `curl` без этого заголовка — поэтому ручная проверка через терминал не видела
   проблему) → **`403 Forbidden`, `Content-Length: 0`**, без тела и без
   `Access-Control-Allow-Origin`. Тот же запрос с `Origin: http://localhost:3000` → `200`.
4. **Причина — в `backend/internal/middleware/cors.go`**: `gin-contrib/cors` настроен со
   статическим `AllowOrigins = ["http://localhost:3000", "https://avtobirzhasi.kz",
   "https://www.avtobirzhasi.kz"]`. `http://localhost:3001` отсутствует в списке — библиотека
   активно отклоняет запрос (`403`), а не просто не добавляет CORS-заголовки. Порт `3001`
   использовался вместо стандартного `3000` только потому, что `3000`/`8080` в этой песочнице
   заняты посторонним проектом (`codeschool-*`) — см. этапы 7Б/8А/8Б-1/8Б-2.

**Заданию было явно сказано не предполагать причину в CORS заранее — она установлена только после
прямого воспроизведения (`curl` с реальным `Origin`), а не принята на веру.**

### 19.2 Фактический URL проблемного запроса

`GET http://localhost:8081/api/regions` с заголовком `Origin: http://localhost:3001` — именно
такой запрос браузер на `http://localhost:3001` посылает через `fetch()` внутри
`lib/api/locations.ts` → `lib/api/client.ts`. `curl` без `Origin` (как при первой ручной проверке
из постановки задачи) не воспроизводит проблему — CORS применяется браузером/сервером только к
запросам с этим заголовком.

### 19.3 Файлы изменены

- `backend/internal/middleware/cors.go` (изменён) — единственная правка логики.
- `backend/internal/middleware/cors_test.go` (новый) — 6 тестов, воспроизводящих проблему и
  проверяющих исправление.

Frontend **не изменялся** — `frontend/lib/api/locations.ts`, `LocationSelector.tsx`,
`QuickSearch.tsx` проверены (раздел 19.1, п.1) и не содержат ошибки; архитектура API-клиента
(`apiFetch`/`API_BASE_URL`) не тронута.

### 19.4 Как исправлено

`CORS()` (`cors.go`) сохранил неизменным фиксированный список (`localhost:3000` +
production-домены) и добавил **опциональное** расширение через переменную окружения
`CORS_EXTRA_ORIGINS` (через запятую, например `http://localhost:3001,http://localhost:5173`) —
не задано → поведение идентично прежнему. **`http://localhost:3001` не прописан в коде как
постоянный адрес** — это была бы порча production-конфигурации ради артефакта одной песочницы;
вместо этого добавлена точка расширения через окружение, которую разработчик на нестандартном
порту включает у себя локально, ничего не меняя в коде. `backend/internal/config/config.go` (где
идёт незавершённая работа над FreedomPay) **не тронут** — переменная читается точечно через
`os.Getenv` прямо в `cors.go`, без изменения структуры конфигурации. Продакшен-домены
(`avtobirzhasi.kz`) не изменены и не удалены.

Локальный запущенный backend-процесс перезапущен с `CORS_EXTRA_ORIGINS=http://localhost:3001`,
чтобы сессия отражала исправление; фронтенд не перезапускался — его не потребовалось менять.

### 19.5 Проверка загрузки регионов, городов и районов

Прямой HTTP-запрос (эмулирующий браузерный, с реальным `Origin`) после перезапуска backend:

- `GET /api/regions` c `Origin: http://localhost:3001` → **`200`**,
  `Access-Control-Allow-Origin: http://localhost:3001`, `Access-Control-Allow-Credentials: true`,
  тело — 20 регионов (проверено парсингом JSON, не только статус-кодом).
- Без заголовка `Origin` (как раньше) → по-прежнему `200` — обратной совместимости с прямыми
  вызовами (curl, серверные вызовы) не нарушено.
- `Origin: http://localhost:3000` (штатный dev-порт) и оба production-домена — по-прежнему `200`

## 21. Этап 8Б-5 — Исправление неполного списка марок автомобилей (реализовано)

### 21.1 Почему отсутствовали марки

Единственный источник списка марок во всём проекте — статический массив `makes` в
`frontend/lib/mock/cars.ts` (проверено: PostgreSQL/Go API марки/модели вообще не хранит и не
отдаёт — `backend/internal/handlers/listings.go`/`cars.go` принимают `make`/`model` как обычные
`string`-поля без какого-либо enum/справочника; убедился прямым grep по `internal/` — ни таблицы,
ни хендлера с «makes»/«brands» нет). Этот массив изначально содержал **ровно те 10 брендов**, что
использует демонстрационный набор `mockCars` в том же файле (`cmd/seed` использует тот же
демо-набор — подтверждено чтением `cmd/seed/main.go`, отдельного справочника марок у seed нет).

только из `makes`), любой бренд вне этих 10 был физически недоступен для выбора — не ошибка
фильтрации/API/несовпадения названий, а изначально **намеренно узкий демо-список**, ни разу не
расширенный с момента создания. Реальные объявления в локальной БД тоже ограничены теми же 10
марками (проверено `SELECT DISTINCT make FROM listings`) — они не «терялись» при отображении, они
физически не могли быть созданы ни с какой другой маркой.

### 21.4 Марка → Модель

Ранее «Модель» была **свободным текстовым полем** (`<Input>`) во всех 4 формах — зависимости от
марки не было вообще (это не было «сломано», такой функциональности просто не существовало до
этого этапа). Реализовано заново, по прямому требованию задания:

- **`ListingForm.tsx`** (создание + редактирование объявления, включая админ-версию — общий
  компонент) и **`RequestForm.tsx`** (создание заявки) — обязательный `<Select>` для модели,
  `disabled`, пока марка не выбрана; при смене марки `setValue("model", "", ...)` сбрасывает
  модель. Модели, привязанные к текущему `make` (`modelsByMake[make]`), плюс — если у уже
  сохранённого объявления/заявки текущее значение `model` не входит в список (устаревший/
  нестандартный ввод) — это значение добавляется первым пунктом, а не пропадает: «существующие
  марки и модели сохранены», как явно требовало задание.
- **`FilterForm.tsx`** (фильтр каталога) и **`QuickSearch.tsx`** (поиск на главной) — необязательный
  `<Select>` («Любая модель»), тот же `disabled`/сброс-при-смене-марки, применяется сразу (без
  debounce — в отличие от прежнего текстового поля, выбор из списка не нуждается в задержке).
  `FilterForm` дополнительно сбрасывает `model` из URL **в одной навигации** вместе со сменой
  `make` (`applyMakeChange`, зеркалит уже существующий паттерн `applyLocationParams`) — не тремя

## 23. Этап 8В-1 — Проверка фотографий автомобилей (реализовано)

### 23.1 Точная причина

Запрос `GET /api/cars?make=Toyota&model=Camry&region=Алматы` (то, что делает поиск на `/cars` из
постановки) реально возвращает **2 активных** объявления Toyota Camry в Алматы (третье — со
статусом `frozen`, не попадает в выдачу активного поиска). Их фотографии проверены напрямую в
`listing_images`:

- Первое (`1c5fa066-57c3-45bf-8b0e-7dc276ea6bfc`) — основное фото
  `http://localhost:8080/uploads/40907ff0b1b5e873a9f809c36f55e453.jpg`.
- Второе (`b66e747c-63a3-4ce7-9008-aeecfd5e1f7d`) — `https://images.unsplash.com/photo-...`.

Прямая проверка HTTP-ответа подтвердила точную причину: `curl
http://localhost:8080/uploads/40907ff0...jpg` → **404** (порт 8080 в этой песочнице занят
посторонним проектом `codeschool-backend`, а не нашим API), но **тот же файл физически существует**
и корректно отдаётся (**200**) с реального backend на `http://localhost:8081/uploads/...` (порт,
на котором в этой сессии реально поднят наш Go-сервер). Корень проблемы —
`backend/internal/config/config.go`: `PublicUploadBaseURL` по умолчанию
(`PUBLIC_UPLOAD_BASE_URL` не задан) равен `"http://localhost:8080"` — это значение попало в URL
при загрузке фото через реальный backend этой сессии, запущенный на нестандартном порту 8081, но
не с соответствующей переменной окружения. **Этот файл — `config.go` — прямо запрещено трогать во
всех этапах этого проекта** (незавершённые изменения FreedomPay), поэтому причина не устранена на
уровне конфигурации/данных, а обработана на уровне фронтенда, как и явно требовало задание (пункты
3–5 постановки).

Важно: URL `http://localhost:8080/uploads/...` **формально проходит** проверку
`isTrustedImageUrl()` (этап 8Б-4) — хост/порт/путь точно совпадают с разрешённым паттерном в
`next.config.js` (`{ protocol: "http", hostname: "localhost", port: "8080", pathname:
"/uploads/**" }`), поэтому `CarCard` до этого этапа передавал его в `<Image>` как «доверенный» —
но реальная HTTP-загрузка в этой конкретной песочнице всё равно проваливалась (неверный порт),
что и проявлялось как «значок повреждённого изображения» — именно то, что описано в задании.

## 24. Шаг 2 — Восстановление настоящих фотографий (реализовано)

### 24.1 Где формировался неправильный URL

`backend/internal/config/config.go`: `PublicUploadBaseURL` вычисляется как
`getEnv("PUBLIC_UPLOAD_BASE_URL", "http://localhost:8080")` — используется дефолт `:8080`, если
переменная окружения не задана явно. `backend/cmd/api/main.go` передаёт это значение прямо в
`handlers.NewUploadsHandler(cfg.UploadDir, cfg.PublicUploadBaseURL)`, а `UploadsHandler.
UploadImages` (`internal/handlers/uploads.go`) строит и возвращает (и тем самым сохраняет в
`listing_images.url`) `publicBase + "/uploads/" + <name>` для каждого нового файла. Когда в этой
сессии backend перезапускался на нестандартном порту `:8081` (порт `:8080` занят посторонним
проектом в этой песочнице) **без** установки `PUBLIC_UPLOAD_BASE_URL`, любая загруженная в тот
момент фотография получала URL с дефолтным `:8080` — портом, на котором **наш** сервер фактически
не слушает. Раздача самого файла (`GET /uploads/:name`, `Serve`) при этом не зависит от порта —
регистронезависимая проверка имени файла и чтение с диска работают на любом порту; ломался только
**сохранённый URL**, не сама раздача.

### 24.2 Проверка `PublicUploadBaseURL` и конфигурации backend

Прочитано (не изменено — `config.go` по-прежнему в списке файлов, которые нельзя трогать во всех
этапах этого проекта из-за незавершённой работы над FreedomPay, и это правило соблюдено и здесь,
хотя явно не повторено в тексте задания): механизм переопределения через `PUBLIC_UPLOAD_BASE_URL`
**уже существовал** и работал корректно, просто не был задействован при последнем перезапуске
backend в этой сессии.

### 24.3 Исправлено

**Backend (операционно, без изменения кода):** backend перезапущен с
`PUBLIC_UPLOAD_BASE_URL=http://localhost:8081` (вместе с уже использовавшимися `PORT=8081` и
`CORS_EXTRA_ORIGINS=http://localhost:3001` из этапа 8Б-3) — подтверждено логом запуска: `listing
photos: writing to ./uploads, serving as http://localhost:8081/uploads/`. Все **новые** загрузки
фотографий с этого момента получают корректный URL. Порт `8081` нигде не прописан в коде — это
значение переменной окружения, специфичное для этой сессии; в обычной локальной среде (порт 8080
свободен) поведение остаётся прежним без каких-либо действий.

**Frontend (код, для уже существующих фотографий со старым `:8080`):**

- `frontend/lib/images/trustedImageUrl.ts`: добавлена `resolveImageUrl(url)` — переписывает
  origin (протокол+хост+порт) URL, только если он одновременно (а) хост `localhost` **и**
  (б) путь начинается с `/uploads/` **и** (в) отличается от текущего настроенного origin backend'а
  (вычисляется из уже существующей `NEXT_PUBLIC_API_URL`, без единого «зашитого» порта). Все
  остальные URL (Unsplash, `api.avtobirzhasi.kz`, уже корректные) возвращаются без изменений —
  никакого воздействия на продакшен-фотографии.
- `TRUSTED_IMAGE_PATTERNS` (та же функция `configuredApiOrigin()`) теперь тоже выводит порт для
  паттерна `localhost` из `NEXT_PUBLIC_API_URL`, а не хардкодит `"8080"`, — иначе переписанный на
  `:8081` URL не прошёл бы собственную проверку `isTrustedImageUrl`.
- `frontend/next.config.ts`: `images.remotePatterns`'ый паттерн для `localhost` тоже больше не

  если бы фронтенд-проверка пропустила URL, `next/image` бросил бы исключение при несовпадении
  этого списка.
- `frontend/components/cars/CarCard.tsx`: `car.imageUrl` теперь сначала проходит через

  `onError` (этап 8В-1) сохранён без изменений как последний рубеж на случай любой другой,
  непредвиденной причины сбоя загрузки.

### 24.4 Как восстановить отображение уже существующих старых фотографий

**Без изменения PostgreSQL** (прямое требование этого шага): переписывание URL происходит
**на лету, в браузере/на сервере рендеринга**, при каждом отображении карточки — `listing_images.
url` в БД остаётся ровно тем же `http://localhost:8080/...`, что и был (проверено: `SELECT` после
правки вернул то же значение, ни один `UPDATE` не выполнялся). Это «безопасный способ» в буквальном
смысле пункта 6 задания: ничего необратимого не делается, восстановление полностью зависит от
текущей конфигурации окружения (`NEXT_PUBLIC_API_URL`) и исчезнет автоматически, если реальный
`PublicUploadBaseURL`/`NEXT_PUBLIC_API_URL` снова совпадут (например, при обычном локальном запуске
без конфликта портов) — тогда `resolveImageUrl` просто не найдёт несовпадения origin и вернёт URL
без изменений, никакого «сломанного» состояния не остаётся при возврате к стандартной конфигурации.

**Альтернатива на будущее (не выполнялась — вне рамок этого шага, PostgreSQL трогать нельзя):**
если потребуется навсегда исправить уже сохранённые записи, есть безопасный путь одноразовым

### 25.2 Причина `onError` (пункт 9–10 задания) — найдена и подтверждена тестом

`CarCard.tsx` (до этой правки) хранил факт ошибки загрузки как **простой булев флаг**:
`const [imageFailed, setImageFailed] = useState(false)`, устанавливаемый в `true` внутри
`onError` и никогда не сбрасываемый обратно. Условие показа фото было `hasTrustedImage &&
!imageFailed`.

**Воспроизведено тестом до исправления** (тем самым выполнен пункт «сначала воспроизведи её
тестом» перед исправлением): смонтирован `CarCard` с URL, для которого сымитирован сбой загрузки
(`fireEvent.error`) → плейсхолдер показан, как и ожидалось. Затем **тот же экземпляр компонента**
получил `rerender()` с новым, заведомо корректным `imageUrl` (не касаясь монтирования/
размонтирования — именно так react-компонент ведёт себя при повторном рендере с новыми пропсами,
включая пересборку кода на лету в dev-режиме Fast Refresh, где React намеренно сохраняет состояние
хуков между правками файла) — **плейсхолдер остался**, хотя новый URL был бы отображён корректно
при первом монтировании. Это и есть подтверждённая причина: `imageFailed` — липкое, ничем не
привязанное к конкретному URL состояние. Как только оно однажды стало `true` (в любой момент —
включая уже устаревшую попытку загрузки с портом 8080 **до** того, как шаг 2 и восстановление
backend/frontend с правильными переменными окружения вступили в силу), оно оставалось `true`
навсегда для этого экземпляра компонента, даже после того как `resolveImageUrl` стал возвращать
полностью рабочий URL. Пользователь видел «исправление применено, но фото всё ещё не грузится» не
потому, что исправление не сработало, а потому что **состояние ошибки одного из предыдущих,
уже неактуальных запросов пережило это исправление** в уже смонтированном компоненте.

Пункт 10 задания («проверь, не сохраняется ли состояние ошибки после изменения URL или повторной
загрузки») — **да, подтверждено, сохранялось**. Это и есть точная причина.

### 25.3 Исправление

Минимальное: `imageFailed: boolean` заменён на `failedImageUrl: string | null` — хранится не факт
«что-то не так», а **конкретный URL**, для которого зафиксирована ошибка. Условие показа —
`hasTrustedImage && resolvedImageUrl !== failedImageUrl`. `onError` теперь пишет
`setFailedImageUrl(resolvedImageUrl)` вместо `setImageFailed(true)`. Следствие: как только
`resolvedImageUrl` меняется на что-то, отличное от того, что реально провалилось (новый пропс,
пересчитанное преобразование после правки кода, обновлённые данные объявления), компонент
автоматически даёт новому URL шанс загрузиться заново — без специального эффекта сброса, чисто
за счёт сравнения значений при каждом рендере (тот же «производное состояние по входным данным»
подход, что уже используется в проекте, например в `FilterForm.tsx`'s `prevValues`). Если же
**тот же самый** URL проваливается повторно — плейсхолдер по-прежнему корректно показывается
(не «мигает» настоящим сломанным изображением браузера).

Ни PostgreSQL, ни `config.go`, ни дизайн/размеры карточки не затронуты — единственная правка:
тип и способ обновления одной переменной состояния в `CarCard.tsx`.
